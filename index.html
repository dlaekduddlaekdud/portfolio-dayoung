Project 01 · 시급 보존과 정산 확정

시급 변경 이후에도 과거 계산 근거 보존 4월 적용 당시 기능

PROBLEM · CONSTRAINT

조교와 코칭은 시급이 다르고 인상은 특정 날짜부터 적용됩니다. 기존 스프레드시트에서는 시급 셀 하나를 고치면 지난달 급여까지 함께 바뀌었습니다.

DECISION
시급 이력 (적용 시작일 기준)
→ 근무 기록 제출 시 근무일에 유효한 시급·계산 금액을 스냅샷으로 저장

시급을 적용 시작일 기준 이력 테이블로 관리하고, 근무 기록을 제출할 때 근무일에 유효한 시급과 계산 금액을 해당 기록 행에 스냅샷으로 저장했습니다.

대안 조회 시 이력 조인으로 당시 시급 역산
기각 이유 이력 수정·삭제에 과거 급여가 종속됨. 정규화를 일부 포기하고 기록 행에 계산 근거를 고정.
RESULT

근무일 기준 시급과 금액이 기록 행에 남고, 급여 계산과 월 경계(2월, 윤년, 30일·31일 달) 경계값을 단위 테스트로 확인했습니다.

검사·집계·확정을 단일 트랜잭션으로 처리 8월 후속 개선

PROBLEM · CONSTRAINT

4월 적용 당시 구현은 대기 기록 확인 → 급여 집계 → 월 정산 확정이 각각 독립된 쿼리여서, 검사와 확정 사이에 다른 기록이 승인되면 확정 금액과 실제 근무 기록이 달라질 수 있었습니다. 당시 사용하던 supabase-js로는 여러 쿼리를 하나의 트랜잭션으로 묶을 수 없었습니다.

DECISION
finalize_payroll()
  대기 기록 검증 → 급여 집계 → 확정 상태 변경 → COMMIT

세 연산을 PostgreSQL finalize_payroll 함수 하나로 옮기고 애플리케이션은 RPC 한 번만 호출하도록 변경했습니다. 요약 행을 FOR UPDATE로 잠그고, 함수 내부에서 관리자 권한을 다시 확인해 검사와 확정이 하나의 원자적 연산으로 처리되도록 구성했습니다.

대안 앱 계층에서 세 쿼리를 순서대로 호출
기각 이유 supabase-js로는 트랜잭션 경계를 둘 수 없어 검사와 확정 사이의 공백이 남고, 함수 밖 권한 검사는 DB 직접 접근 시 우회됨.
RESULT

대기 기록이 있으면 확정이 거부되고 요약 행이 남지 않음을 확인했습니다. 반려 기록 제외와 재확정 시 금액 유지도 관리자 로그인 상태의 RPC 통합 테스트로 검증했습니다.

동시 확정을 직렬화하기 위한 잠금을 적용했으며, 동시 요청 테스트는 수행하지 않았습니다.

기간 계산을 SQL로 옮기면서, 시간대 변환 때문에 말일 대기 기록이 검사 범위에서 빠지던 버그도 함께 사라졌습니다.

재시도 이후에도 이전 실패 원인 보존

PROBLEM · CONSTRAINT

월 마감은 수동 실행과 Scheduler 실행이 겹칠 수 있고, 실패하면 다시 실행해야 하는 작업입니다. 현재 마감 상태와 실행 기록을 한 행에서 관리하면 재시도 과정에서 이전 실패 원인이 덮어써집니다.

DECISION
close_period (현재 상태) : OPEN / CLOSED
close_run    (실행 이력) : RUNNING / SUCCESS / FAILED / SKIPPED

현재 상태와 실행 이력을 별도 엔티티로 분리했습니다. 마감 실행 시 기간 행을 비관적 쓰기 잠금으로 보호해 동시 마감을 직렬화하고, 실패하면 집계 결과는 롤백하되 REQUIRES_NEW로 실패 이력과 원인은 별도 트랜잭션에 보존했습니다. 이미 닫힌 기간의 요청은 결과를 변경하지 않고 SKIPPED 실행 이력만 남겨 재시도가 안전하도록 했습니다.

대안 마감 상태와 마지막 실행 결과를 단일 행에 저장
기각 이유 실패 원인이 덮어써지고 본 트랜잭션 롤백 시 이력도 사라짐. 기간 행만 잠가 상태와 이력을 분리.
RESULT

기간 행이 없는 같은 기간의 최초 동시 마감 요청에도 성공 결과가 한 벌만 생성되고, 집계 실패 시 기간이 OPEN으로 남아 FAILED가 기록되며 재실행 시 새 attempt로 SUCCESS가 되는 것을 확인했습니다.

원본 수정 대신 반대 금액·정정 행으로 사후 정정

DECISION
OPEN PERIOD    원본 → CANCELLED → CANCEL_OFFSET

열린 기간의 취소와 닫힌 기간의 회계 정정을 분리했습니다. 마감 후에는 기존 원장을 직접 수정하지 않고 반대 금액의 REVERSAL과 수정된 CORRECTION 행을 추가하며, 실행자와 사유는 append-only 감사 로그에 기록해 변경 경로를 남겼습니다.

PROBLEM 1 · 동시 등록 간 교착

입고·송장을 등록할 때마다 마감 여부 확인이 기간 행을 만들고 배타 잠금을 걸었습니다. 같은 달의 모든 등록이 행 하나에서 직렬화되고, insert ignore가 잡은 공유 잠금이 배타 잠금으로 올라가는 과정이 겹쳐 교착이 생기는 구조였습니다.

DECISION

마감 여부 확인은 읽기 검증이므로 행을 만들지 않고 공유 잠금으로만 읽도록 분리했습니다. 행이 없으면 한 번도 마감하지 않은 열린 기간으로 판단합니다. 기간 행이 이미 있을 때는 진행 중인 마감이 잡은 배타 잠금과 배제됩니다.

RESULT

마지막 남은 수량에 대한 동시 입고 등록이 마감 기간 확인 단계에서 교착 없이 한 건만 성립함을 테스트로 확인했습니다.

PROBLEM 2 · 재실행 경로의 LockTimeoutException

잠금 보유 구간을 줄이려고 기간 행 등록만 별도 트랜잭션으로 분리하자, 이미 닫힌 기간을 다시 마감할 때 등록이 호출자 자신의 배타 잠금을 기다리다 LockTimeoutException이 발생했습니다.

DECISION

등록과 잠금을 호출자와 같은 트랜잭션에서 수행하도록 되돌리고, 실패 이력만 별도 트랜잭션으로 보존하는 경계를 ADR에 기록했습니다.

RESULT

닫힌 기간 재실행이 결과를 바꾸지 않고 SKIPPED 실행 이력만 남기는 것을 테스트로 확인했습니다. 기존 기간 행에 마감 요청 두 건이 정확히 겹치는 경우의 교착 가능성은 남은 한계로 ADR에 기록했고, 기간 행이 없을 때 등록과 최초 마감이 겹치는 조합은 테스트하지 않았습니다.

PROBLEM

DECISION
신청 행   PESSIMISTIC_WRITE → PENDING 확인

신청 APPROVED → 멤버 생성 + 인원 증가 → COMMIT

CONCURRENCY TEST

잔여 정원 1명 상태에서 동시 승인 요청 20개 × 반복 실행 20회를 검증했습니다. 확인 기준은 두 층입니다 — 각 반복마다 승인 성공 1건 / 정원 초과 실패 19건이 나오는가, 그리고 트랜잭션 종료 후 DB에서 승인된 신청 1건, 개설자를 포함한 스터디 승인 인원 2명, 멤버 2명으로 정원 2명과 맞는가. 응답 결과만 세면 통과했더라도 테이블 간 불일치가 남을 수 있어, 상태 검증을 응답이 아니라 DB 최종 상태에 뒀습니다. 이 테스트는 정합성 검증이며, 처리량이나 응답 지연은 측정하지 않았습니다.
