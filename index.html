Background

약 4년간 영어학원에서 조교와 조교 총괄로 근무하며 스케줄, 근무 기록 확인, 월별 급여 정산 검토를 담당했습니다. 근무 기록은 조교가 개인적으로 신고하면 총괄이 받아 확인하는 방식이었고, 데이터 관점에서 다음 네 가지 결함이 반복됐습니다.

  • 단일 원장 부재 — 기록이 개인 메시지와 구두로 도착해, 총괄의 기억과 대화 내역이 사실상의 원장 역할을 했습니다.
  • 집계 자동화 부재 — 조교 최대 23명의 신고 시간을 하나씩 대조하는 데 매월 약 2시간이 걸렸습니다.
  • 검증 장치 부재 — 누락·중복 신고나 시급 적용 착오가 있어도, 사람이 눈으로 비교하는 것 외에 발견할 방법이 없었습니다.
  • 확정 근거 미보존 — 급여 확정 뒤 이의가 들어와도 어떤 기록으로 얼마를 계산했는지 재현할 수 없었습니다.

이 네 결함은 각각 다른 기능이 아니라 하나의 질문으로 수렴했습니다 — "어떤 기록이 어느 시점부터 확정되고, 이후에도 당시 계산 근거를 재현할 수 있는가." 시스템의 핵심 문제를 CRUD가 아닌 이 질문으로 정의하고 설계했습니다.

근무 기록 → 관리자 확인 → 수정·승인 → 월별 집계 → 급여 확정
실제 사용 범위 · 학원의 공식 인사 시스템을 대체하거나 조교 전원이 직접 사용한 서비스는 아닙니다. 기존 방식으로 전달된 조교들의 근무 기록을 본인이 다시 확인하는 운영자용 정산 보조 도구로 사용했고, 약 1개월간 조교 23명분의 실제 근무·급여 데이터를 처리했습니다.

시급이 바뀌어도 과거 급여 계산 근거를 보존

PROBLEM

현재 시급만 참조해 급여를 계산하면 이후 시급이 변경됐을 때 과거 급여까지 달라질 수 있습니다.

DECISION
Hourly Rate History (적용 시작일 기준 이력 관리)
    │
    ▼
Worklog 제출
  ├── applied_hourly_rate 저장
  └── calculated_pay 저장

시급을 적용 시작일 기준 이력 테이블로 관리하고, 근무 기록 제출 시점의 적용 시급과 계산 금액을 해당 기록 행에 스냅샷으로 저장했습니다.

대안 조회 시 이력 조인으로 당시 시급 역산
기각 이유 이력 수정·삭제에 과거 급여가 종속됨. 정규화를 일부 포기하고 기록 행에 계산 근거를 고정.

검증: 급여 계산 및 월 경계

검사와 확정을 하나로 묶어 정산 불일치를 방지

PROBLEM

초기 구현은 대기 기록 확인 → 급여 집계 → 월 정산 확정 연산이 각각 독립적으로 실행돼, 검사와 확정 사이에 다른 기록이 승인되면 확정 금액과 실제 근무 기록이 달라질 가능성이 있었습니다.

DECISION
finalize_payroll()
  대기 기록 검증 → 급여 집계 → 확정 상태 변경 → COMMIT

세 연산을 PostgreSQL finalize_payroll 함수 하나로 옮기고 애플리케이션은 RPC 한 번만 호출하도록 변경했습니다. 요약 행을 FOR UPDATE로 잠그고, 함수 내부에서 관리자 권한을 다시 확인해 검사와 확정이 하나의 원자적 연산으로 처리되도록 구성했습니다.

대안 앱 계층에서 세 호출을 트랜잭션으로 묶기
기각 이유 왕복 3회로 잠금 유지 시간이 늘고, DB 직접 접근 시 권한 검증이 우회됨.

검증: 대기 기록 존재 시 확정 차단 · 재확정 시 기존 금액 유지

우회 요청에서도 확정 월의 데이터 변경을 차단

PROBLEM

애플리케이션 검증만으로 확정 데이터를 보호하면, 검증을 거치지 않는 경로(직접 쿼리, 클라이언트 우회)에서 확정된 월의 기록이 변경될 수 있습니다.

DECISION
Application  사용자에게 적절한 오류 안내    — 첫 번째 방어선
Database     우회된 요청에서도 무결성 보호  — 마지막 방어선

확정 월의 근무 기록 변경은 PostgreSQL 트리거로 차단하고, 승인·반려 데이터에 대한 사용자 직접 수정은 RLS로 제한했습니다. 두 계층의 역할을 "안내"와 "보호"로 분리해 어느 한쪽이 뚫려도 확정 데이터가 바뀌지 않도록 구성했습니다.

Business Flow

REQUESTER  구매요청 작성 → 제출
    ↓
BUYER      승인 / 거절 → 발주 생성·발송
    ↓
부분입고 · 분할송장 접수 → 3-Way Matching → MATCHED / HOLD → 미착 원장
    ↓
ADMIN      수동 / Scheduler 월 마감 → 마감 스냅샷 보존 → REVERSAL / CORRECTION

구매요청 한 건의 생성에서 끝내지 않고 입고·송장·원장·마감·사후 정정까지 데이터의 생명주기 전체를 구현했습니다. 각 단계 경계에서 "어떤 상태 전이가 허용되는가"와 "실패 시 무엇을 남기는가"를 먼저 정의하고, 트랜잭션·잠금·DB 제약·감사 이력을 그 정의에 따라 서로 다른 역할로 배치했습니다.

분할 도착해도 발주 라인 누적값으로 정확히 대사

PROBLEM

한 번의 발주가 여러 번 입고되고 송장 역시 나뉘어 들어올 수 있어, 부분 송장을 발주 전체 금액과 직접 비교하면 정상 거래까지 가격 불일치로 판단할 수 있습니다.

DECISION

입고 라인과 송장 라인이 발주 라인을 직접 참조하도록 구성하고, 발주 라인을 집계 기준으로 누적 입고량과 누적 송장량을 계산해 MATCHED / HOLD_QUANTITY / HOLD_PRICE 상태로 관리했습니다. 추가 입고가 발생하면 기존 HOLD 건도 다시 대사해 최종 상태가 도착 순서에 의존하지 않도록 했습니다.

대안 송장 접수 시 발주 문서 단위로 즉시 대사
기각 이유 분할 도착을 표현하지 못해 정상 거래도 HOLD로 남음. 라인 간 정합성 검증 부담을 감수.

검증: 부분입고·분할송장 · 가격·수량 HOLD · 추가 입고 후 재대사

마감 실패와 재시도에도 이전 실패 원인을 보존

PROBLEM

현재 마감 상태와 마감을 실행했던 기록을 하나의 행에서 관리하면 재시도 과정에서 이전 실패 원인이 덮어써질 수 있습니다.

DECISION
close_period (현재 상태) : OPEN / CLOSED
close_run    (실행 이력) : RUNNING / SUCCESS / FAILED / SKIPPED

현재 상태와 실행 이력을 별도 엔티티로 분리했습니다. 마감 실행 시 기간 행을 비관적 쓰기 잠금으로 보호해 동시 마감을 직렬화하고, 실패하면 집계 결과는 롤백하되 REQUIRES_NEW로 실패 이력과 원인은 별도 트랜잭션에 보존했습니다. 이미 닫힌 기간의 요청은 결과를 변경하지 않고 SKIPPED 실행 이력만 남겨 재시도가 안전하도록 했습니다.

대안 마감 상태와 마지막 실행 결과를 단일 행에 저장
기각 이유 실패 원인이 덮어써지고 본 트랜잭션 롤백 시 이력도 사라짐. 기간 행만 잠가 상태와 이력을 분리.

검증: 동시 월 마감 · 마감 실패 후 재시도

원본을 수정하지 않고 마감 후 정정 이력을 보존

PROBLEM

마감 이후 원본 문서나 기존 원장 금액을 직접 수정하면 과거 마감 결과를 재현하기 어렵습니다.

DECISION
OPEN PERIOD    원본 → CANCELLED → CANCEL_OFFSET
CLOSED PERIOD  Original Ledger → REVERSAL → CORRECTION

열린 기간의 취소와 닫힌 기간의 회계 정정을 분리했습니다. 마감 후에는 기존 원장을 직접 수정하지 않고 반대 금액의 REVERSAL과 수정된 CORRECTION 행을 추가하며, 실행자와 사유는 append-only 감사 로그에 기록해 변경 경로를 남겼습니다.

대안 원본 UPDATE 후 변경 전 값을 이력 테이블에 저장
기각 이유 재현에 이력 역추적이 필요하고 누락 시 복구 불가. 원장 자체를 append-only로 유지.

PROBLEM

정원이 한 자리 남은 상태에서 여러 요청이 동시에 승인되면 각 트랜잭션이 같은 승인 인원을 읽고 모두 통과할 수 있습니다.

DECISION
신청 행   PESSIMISTIC_WRITE → PENDING 확인
스터디 행 PESSIMISTIC_WRITE → 남은 정원 확인
신청 APPROVED → 멤버 생성 + 인원 증가 → COMMIT

신청 행을 먼저 잠가 같은 신청의 중복 상태 전이를 차단하고, 스터디 행을 잠가 동일 스터디의 정원 검증을 직렬화했습니다. 잠금 순서를 신청 → 스터디로 고정해 두 자원을 잠그는 트랜잭션 간 교착을 피했습니다.

대안 버전 컬럼을 사용하는 낙관적 잠금
기각 이유 마지막 자리처럼 충돌이 집중되는 구간에서 재시도 부담이 커짐. 비관적 잠금으로 승인 직렬화.
CONCURRENCY TEST

잔여 정원 1명 상태에서 동시 승인 요청 20개 × 반복 실행 20회를 검증했습니다. 확인 기준은 두 층입니다 — 각 반복마다 승인 성공 1건 / 정원 초과 실패 19건이 나오는가, 그리고 트랜잭션 종료 후 승인된 신청 수·스터디 승인 인원·실제 멤버 수 세 값이 모두 일치하는가. 응답 결과만 세면 통과했더라도 테이블 간 불일치가 남을 수 있어, 상태 검증을 응답이 아니라 DB 최종 상태에 뒀습니다.

TRANSACTION ROLLBACK

승인 과정 중 멤버 저장에서 강제로 예외를 발생시킨 뒤, 신청 상태 PENDING · 승인 인원 개설자 1명 · 신청자 Member 없음 세 가지 최종 상태를 다시 조회해 복원 여부를 확인했습니다. 예외가 던져졌는지가 아니라 여러 테이블의 상태가 함께 이전으로 돌아갔는지를 검증 대상으로 삼았습니다.
